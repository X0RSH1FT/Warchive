Executive Summary

OpenCode is not merely a chat interface; it is a sophisticated, multi-modal AI coding agent designed to manage the entire software development lifecycle—from initial planning and context gathering to iterative building and deployment. Mastering OpenCode requires understanding that its commands exist in three distinct operational layers: the Command Line Interface (CLI) for setup and environment management, the Terminal User Interface (TUI) for internal state control and context manipulation, and specialized Keyboard Shortcuts for rapid workflow execution.

This report serves as the definitive guide to these command structures. It synthesizes all known commands, explaining not only what a command does but critically, why it matters in the development process. By mastering the sequence of opencode auth login, /init, and leveraging agent-specific keybinds, users can transform OpenCode from a powerful tool into an indispensable extension of their own cognitive workflow, dramatically accelerating coding velocity and reducing context switching overhead [Finding 1, Finding 5].

Quick Guide

  1. Install: Run opencode auth login to connect the agent to your LLM provider.
  2. Initialize: Navigate to a project folder and run opencode [project] followed by /init to build the foundational context map.
  3. Plan/Build Cycle: Use the Tab key to switch between suggesting changes (Plan mode) and executing them (Build mode).
  4. Contextual Search: Reference specific files or code blocks using @key in the TUI prompt.
  5. Session Management: Use <leader>n to start a new, isolated work session for focused tasks.

Step 1: Establishing the Foundation – CLI Environment Setup

The Command Line Interface (CLI) is the external control panel for OpenCode. These commands are run before you enter the interactive coding environment; they manage credentials, plugins, and the overall health of your installation [Finding 2, Finding 5]. Understanding this layer is crucial because a failure here prevents any subsequent TUI work from functioning correctly.

Authentication and Model Selection

The very first step in using OpenCode effectively is establishing secure communication with an external AI brain. This is accomplished via the authentication command: opencode auth login. This process does more than just inputting keys; it establishes a persistent, encrypted connection that allows OpenCode to access powerful LLM capabilities [Finding 2].

Following successful authentication, users must manage their model selection using opencode models [provider]. This function is vital because different providers (e.g., OpenAI vs. Anthropic) offer varying performance characteristics, cost structures, and context window sizes. By listing available models, the user can select the optimal backend for a specific task—for instance, choosing a massive model for complex refactoring versus a smaller, faster model for simple linting checks [Finding 5].

Project Scaffolding and Extension

OpenCode's power is modular, meaning it relies heavily on plugins and custom agents. The CLI provides the tools to manage this complexity:

  • Plugin Management: To extend OpenCode’s functionality beyond its core features (e.g., adding support for a niche framework or database), the user must run opencode plugin install <npm-module> [Finding 5]. This command updates the agent's internal capability set, allowing it to recognize and utilize new tools.
  • Agent Creation: The most advanced CLI function is creating specialized agents using opencode agent create. An agent is essentially a defined role or workflow (e.g., "Security Auditor," "Database Migrator"). By defining these roles externally, users can ensure that the AI adopts a specific persona and set of rules before even opening a file [Finding 3].
  • Serving Capabilities: For enterprise integration, opencode serve is critical. This command transforms OpenCode into an external API endpoint (HTTP server). Instead of running it only in your local terminal, you can now integrate its advanced logic—such as code analysis or natural language querying—into a web dashboard or CI/CD pipeline [Finding 5].

Tip: Always verify the installed version and available plugins using opencode --version to ensure compatibility with recent LLM API changes.

Step 2: Entering the Interactive Workspace – Context Initialization (TUI)

Once the CLI environment is stable, the user must transition into the Terminal User Interface (TUI). This shift in operational mode fundamentally changes how commands are interpreted. The TUI is where OpenCode "thinks" and interacts with your codebase [Finding 1].

Launching and Context Mapping

The primary entry point is opencode [project]. This command launches the full, interactive session within the specified directory. However, merely launching the agent is insufficient; the agent must be given context. The single most critical internal command is /init.

When a user runs /init, OpenCode performs a deep, recursive analysis of the entire codebase—reading file structures, analyzing dependencies, and generating comprehensive documentation summaries [Finding 2, Finding 8]. This process generates global context files (such as agents.md) that serve as the agent's "memory" of your project structure. Without running /init, OpenCode operates blind, treating every request as if it were in a vacuum, leading to inaccurate or generic code suggestions [Finding 9].

Managing Context and Memory

The AI’s ability to maintain context is limited by token count—its working memory capacity. As the conversation grows, older details are forgotten unless actively managed. This leads to the necessity of two key TUI commands:

  • /compact: When the session history approaches its limit, running /compact instructs OpenCode to summarize the previous chat logs and context window into a dense, efficient summary. This action drastically reduces token usage while retaining the core narrative thread of the conversation [Finding 2, Finding 9].
  • File Referencing (@key): Instead of relying on general memory, users must actively ground the AI in specific code locations using the @key syntax (e.g., @packages/utils/index.ts). This manual referencing forces OpenCode to pull the exact contents and structure of that file into its immediate working context, ensuring that suggestions are highly accurate and relevant to the existing codebase [Finding 8].

Step 3: Orchestrating Workflows – Agents, Tools, and State Control (TUI & Keybinds)

This section covers the advanced mechanics of controlling the agent's behavior. OpenCode is designed around specialized roles (Agents), which are invoked via both internal commands and rapid keybinds.

Agent Management and Role Switching

OpenCode recognizes that a single AI model cannot perform all tasks optimally. Therefore, it implements multiple specialized agents: General (for broad queries), Plan (for architectural design), Build (for implementing code changes), and Explore/Scout (for deep research).

  • Internal Listing (/agents): The command /agents allows the user to view every defined agent and explicitly set which one is active. This is useful when switching between roles manually [Finding 7].
  • Keybind Efficiency: For maximum speed, users should rely on Agent Cycling (typically using the Tab key) or the @mention syntax (@general help me search...) [Finding 1, Finding 2]. Using these methods bypasses typing and immediately switches the agent's focus to the required role.

File Manipulation and State Control

The built-in system tools are essential for treating OpenCode not just as a chat bot, but as an integrated development environment (IDE) extension.

  • Reading/Writing Files: The read <file> and write <code> commands allow the user to programmatically interact with the file system through the agent's prompt [Finding 6]. For example, instead of copy-pasting a large block of code into the chat, you can use read src/config.yaml to feed its contents directly and reliably into the context window for analysis.
  • Revision Control (/undo, /redo): The ability to execute /undo or /redo is critical because it provides a localized revision history within the session state [Finding 8]. This means that if an agent makes a faulty suggestion or change, you can instantly revert the system's internal state without needing external Git commands.

Step 4: Advanced Workflow Integration and Scaling (The Professional Use Case)

For professional developers, OpenCode is used not just for coding, but for managing the entire development pipeline. This requires understanding how to leverage its integration points and scaffolding tools.

The Structured Plan/Build Cycle

OpenCode enforces a structured workflow that mirrors professional software development practices: Plan $\rightarrow$ Build $\rightarrow$ Test.

  1. Planning (Plan Mode): When you ask the agent for a feature, it first enters "Plan mode." It will not write code; instead, it generates detailed architectural suggestions, file changes, and step-by-step instructions [Finding 8]. This forces human review at the critical design stage.
  2. Building (Build Mode): Once you approve the plan, switching to "Build mode" allows OpenCode to execute the suggested changes directly into your project files, managing diffs and ensuring consistency across multiple modules [Finding 8].

This structured approach is a massive improvement over simple chat-based code generation because it forces explicit agreement on scope before any irreversible file modifications occur.

Customization and Knowledge Playbooks

OpenCode supports advanced customization through scaffolding commands:

  • /scaffold command <CommandName>: This allows the user to define entirely new, reusable internal shortcuts or workflows that are specific to their team's conventions (e.g., a custom command for "Running Pre-Commit Hooks").
  • /scaffold skill <SkillName>: A 'skill' is essentially a knowledge playbook—a structured set of instructions and best practices related to a domain (e.g., "AWS Deployment Skill" or "React State Management Playbook") [Finding 9]. By scaffolding these, users ensure that the agent always adheres to company-specific standards, regardless of who is using it.

This level of customization elevates OpenCode from a general-purpose AI tool into a highly specialized, domain-aware development partner.

Common Mistakes and Pitfalls

  1. Ignoring Context Initialization: The most common mistake is treating the TUI like a blank slate. If you forget to run /init after cloning a new repository, OpenCode will have zero understanding of your project's architecture, leading to incorrect assumptions about dependencies or file relationships [Finding 9].
  2. Context Overload (The "Memory Leak"): Allowing the conversation history to grow unchecked without using /compact is detrimental. The agent will eventually hit its token limit, and even before that, performance degrades as the model struggles to prioritize relevant information from thousands of tokens of chat history [Finding 2].
  3. Mixing CLI and TUI Commands: Do not attempt to run a TUI command (like /agents) directly in your system terminal prompt. These commands are only valid after you have successfully executed opencode [project] and entered the interactive session [Finding 1].
  4. Assuming Persistence: While OpenCode has session management (opencode export), users must remember that complex, multi-day work sessions should be explicitly saved using the appropriate CLI commands to ensure the full context history is preserved for later resumption [Finding 2].
