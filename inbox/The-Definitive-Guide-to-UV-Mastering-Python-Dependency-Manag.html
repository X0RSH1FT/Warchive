Executive Summary

UV is rapidly emerging as the most powerful, high-performance tool in the modern Python developer toolkit. Designed by Astral, it aims to solve the long-standing pain points associated with traditional package managers like pip, poetry, and venv—namely, slow dependency resolution, complex environment setup, and inconsistent build processes. This comprehensive guide serves as a definitive cheatsheet and deep dive into UV's command line interface (CLI). It moves beyond simple syntax listing to explain the workflow of modern Python development: how to initialize a project, manage dependencies across different groups (development vs. production), ensure absolute reproducibility via lockfiles, and execute code safely within isolated environments. By mastering these commands, developers can dramatically accelerate their setup time and increase the reliability of their deployments.

Quick Guide

  1. curl -sSf [https://astral.sh/uv/install.sh](https://astral.sh/uv/install.sh) | sh: Install UV globally on your system.
  2. uv venv my-project: Create a dedicated, isolated virtual environment for your project.
  3. uv add requests: Add a core dependency (e.g., requests) to the project and update the manifest.
  4. uv add --dev pytest: Add a package specifically for development tools (like testing frameworks).
  5. uv add -r requirements.txt: Import dependencies from an existing standard requirements file.
  6. uv lock: Generate or update the comprehensive dependency lockfile (uv.lock) to ensure reproducibility.
  7. uv sync: Install all packages listed in the uv.lock file into the active environment.
  8. uv run python myscript.py: Execute a script safely within the isolated virtual environment without manual activation.
  9. uv tool install ruff: Install an external utility (like a linter) that isn't a Python package.
  10. uv build: Package your project into distributable formats (.whl, .tar.gz) ready for PyPI.

Step 2: Environment Management and Scaffolding (Isolation)

The core principle of modern Python development is isolation. UV excels at this, ensuring that Project A's dependencies cannot accidentally conflict with Project B or your system-wide Python installation. This process involves two distinct actions: creating the isolated environment (venv) and initializing the project structure (init).

Creating Isolated Virtual Environments

The uv venv command is the primary mechanism for establishing a clean, dedicated workspace. By default, UV creates this virtual environment in a hidden directory named .venv within your current working directory. This convention makes it easy to locate and manage the isolated dependencies.

  • Basic Creation: Running uv venv establishes the basic structure needed to house Python interpreters and installed packages.
  • Custom Naming: If you are managing multiple projects in one folder, using a specific name is best practice: uv venv my-project. This keeps your environment directories clean and organized.
  • Version Control (Crucial): UV offers powerful control over the interpreter version itself. If your project requires Python 3.12 for compatibility reasons, you must specify it: uv venv --python 3.12. UV is smart enough to download and configure that specific interpreter if it isn't already available on your system Ensures compatibility across different projects.

Project Initialization and Scaffolding

UV understands that a project requires more than just an environment; it needs structure. The uv init command handles the scaffolding, setting up the necessary configuration files—most importantly, the pyproject.toml file—which serves as the single source of truth for all dependencies and build metadata.

  • Standard Project: For a general application, uv init [project_name] creates a boilerplate structure suitable for most Python apps, including basic dependency placeholders.
  • Library Focus: If you are building a reusable package (a library), use the specialized command: uv init --lib. This is highly recommended because it automatically sets up build system requirements and metadata necessary to make your code publishable on PyPI Recommended when building reusable packages.

Step 3: Dependency Management (The Core Workflow)

This section represents the heart of UV's functionality, replacing the complex interplay between pip install, poetry add, and manual manifest editing. UV centralizes all dependency management into a single, cohesive workflow using the add, remove, lock, and sync commands.

Adding Packages: The uv add Command

The uv add command is revolutionary because it does two things simultaneously: 1) It updates your project's manifest (pyproject.toml) with the package name; and 2) It attempts to resolve and install that dependency into the active virtual environment, ensuring immediate consistency Example: uv add requests.

Advanced Dependency Sources

UV dramatically expands where dependencies can come from, offering solutions for complex enterprise environments:

  1. Requirements Files: For legacy projects or those migrating from older tools, UV supports standard requirements files: uv add -r requirements.txt. This allows bulk importing of known dependency sets [Finding 2].
  2. Local/Editable Installs: When developing multiple related packages, you often need to install a package that lives on your local filesystem (e.g., in an adjacent directory). UV handles this gracefully using editable installs: uv add --editable ../projects/bar/. This ensures changes are immediately reflected without re-installing the entire environment [Finding 2].
  3. Source Control (Git): For dependencies that haven't been packaged yet, or for testing against a specific branch of development code, UV integrates directly with Git: uv add git+<url> --branch main. This capability is critical in CI/CD pipelines and early-stage development [Finding 2].
  4. Platform Specificity: For highly specialized applications (e.g., machine learning models that only run on Linux), you can define dependencies with platform constraints: uv add "jax; sys_platform == 'linux'". This prevents the package manager from attempting to install incompatible binaries [Finding 2].

Managing Dependency Groups and Extras

Modern projects rarely have a single set of dependencies. They often require separate groups for testing, linting, documentation generation, or optional features (e.g., PDF export). UV provides granular control over these groups:

  • Development Dependencies (--dev): These are tools required only during development and testing (like pytest). Using uv add --dev pytest ensures that the package is listed in a dedicated group within your manifest, keeping production dependencies clean [Finding 9].
  • Custom Groups: For complex projects, you can define arbitrary groups (e.g., 'test', 'lint'). The command structure is: uv add --group <name> <pkg>. This allows for highly organized dependency manifests [Finding 3, Finding 8].
  • Optional Extras (--optional): These are features that a user might want but aren't required for the core functionality (e.g., if your app supports both web and desktop interfaces, the 'web' dependencies are optional). uv add --optional viz matplotlib defines this feature set [Finding 3].

Locking and Reproducibility: The lock vs. sync Distinction

This is arguably the most critical conceptual leap when moving to UV. Dependency resolution is complex; simply listing a package name (requests) does not guarantee which version will be installed, as many packages have transitive dependencies (packages that they depend on).

To solve this, UV introduces two distinct commands: uv lock and uv sync. They must be understood as sequential steps in the development lifecycle.

1. The Lockfile (uv lock)

The purpose of uv lock is to generate a reproducible snapshot of your entire dependency graph into a file (the uv.lock). When you run this command, UV resolves every single package and its exact version number—including the transitive dependencies—and records them in the lockfile [Finding 4].

When to use uv lock: Always run this command immediately after making changes to your dependency manifest (e.g., running uv add requests). This captures the current, working state of your project's requirements.

2. Synchronization (uv sync)

The purpose of uv sync is not to resolve dependencies; it is simply to install them. It reads the exact versions listed in the uv.lock file and installs them into the virtual environment. This process guarantees that every machine, including CI/CD servers, will install the exact same package versions, eliminating "it works on my machine" bugs Use in CI/CD or deployment.

Targeted Updates and Control

UV provides fine-grained control over these commands:

  • Full Update: To update every single dependency to its latest compatible version and generate a new lockfile, use uv lock --upgrade.
  • Targeted Upgrade: If you only want to upgrade one package (e.g., from requests==2.28 to the latest minor release) without touching everything else, use: uv lock --upgrade-package requests. This is safer and faster than a full upgrade [Finding 10].
  • Group Control: When deploying production code, you do not want development tools (like pytest) installed. You can control this during synchronization:
    • uv sync: Installs everything (production + dev).
    • uv sync --no-dev: Skips the entire development group, resulting in a lean, optimized production environment [Finding 9].
    • uv sync --group test: Only installs packages necessary for testing.

Step 4: Execution, Tooling, and Deployment (The Workflow)

Once dependencies are installed and locked, UV provides specialized commands to run code safely, manage external tools, and prepare the project for distribution.

Running Code Safely with uv run

Manually activating a virtual environment (source .venv/bin/activate) is cumbersome and error-prone. The uv run command solves this by executing any script or command directly within the context of the managed virtual environment, without requiring manual activation This is the preferred method.

Example: Instead of typing source .venv/bin/activate && python myscript.py, you simply run:

uv run python myscript.py

Furthermore, uv run supports group-specific execution: * uv run --group test pytest: This ensures that the testing framework (pytest) is available and correctly configured for the duration of the command, even if it's not a core dependency.

Execution Flags: For maximum reliability in automated systems (like CI/CD), UV offers flags to enforce lockfile integrity: * --locked: Forces the execution environment to strictly adhere to the versions specified in uv.lock. If any package version has been allowed to drift, the command fails immediately. * --frozen: A read-only mode that uses the lockfile without attempting any checks for updates or changes.

Managing External Tools (pipx Replacement)

Many developer utilities (linters like ruff, formatters like black, type checkers like mypy) are not standard Python libraries but standalone command-line tools. Historically, managing these required separate tools like pipx. UV integrates this functionality directly:

  1. Installation: Use uv tool install <tool> to download and manage the utility in an isolated cache.
  2. Execution: Use uv tool run <tool> [args] to execute it safely, ensuring that the tool runs with its own dedicated dependencies.

This capability makes UV a true "all-in-one" solution for developer tooling.

Building and Exporting Artifacts

When your project is stable and ready to be shared, you need two final steps: building and exporting.

  • Building (uv build): This command takes your source code and the metadata in pyproject.toml and generates standard Python distribution artifacts—the wheel (.whl) and the source archive (.tar.gz). These are the files you upload to PyPI or distribute directly Essential step before publishing a package.
  • Exporting (uv export): This is useful for generating compatibility files. Instead of relying solely on the lockfile, uv export can output the entire dependency set into various standard formats (e.g., traditional requirements.txt, or modern SBOM formats like CycloneDX), making it easier to integrate with legacy systems [Finding 1].

Common Mistakes and Pitfalls

Even with a powerful tool like UV, developers can fall into common traps related to the complexity of dependency management.

Mistake 1: Confusing uv lock and uv sync

The Error: Running uv add requests and then immediately running uv sync. The Problem: The add command updates the manifest (pyproject.toml), but it does not update the lockfile. If you run sync without first running lock, your environment might be installed using a resolution state that was never formally recorded, leading to non-reproducible builds. The Fix: The mandatory workflow is: Change Dependencies $\rightarrow$ uv lock $\rightarrow$ uv sync.

Mistake 2: Forgetting the --dev Flag

The Error: Running uv add pytest without specifying a group, treating it as a core dependency. The Problem: This bloats your production dependencies and increases the size of your final deployment package unnecessarily. The Fix: Always use uv add --dev <pkg> for testing tools, linters, or documentation generators.

Mistake 3: Over-reliance on System Python

The Error: Running scripts directly using the system's global python interpreter instead of uv run. The Problem: The script will use whatever dependencies are globally available—which may be outdated, incompatible, or entirely missing—leading to runtime errors that are nearly impossible to debug. The Fix: Always wrap execution commands with uv run <command> to guarantee the correct isolated environment is used.

Mistake 4: Ignoring the Lockfile in Version Control

The Error: Committing only pyproject.toml but forgetting to commit uv.lock. The Problem: If you only commit the manifest, other developers or CI/CD pipelines will run a fresh dependency resolution (uv lock) which might resolve dependencies differently based on their local machine state, leading to subtle, hard-to-debug version mismatches across environments. The Fix: The uv.lock file must be committed alongside your manifest. It is the contract for reproducibility.

Conclusion: Answering the Question

UV is not merely a replacement for pip; it represents a fundamental shift in how Python projects are structured, managed, and deployed. By integrating advanced features—such as explicit support for development groups (--dev), granular control over optional dependencies (--optional), direct Git source integration, and most critically, the clear separation between dependency resolution (uv lock) and environment installation (uv sync)—UV provides a robust, high-performance solution to Python's long-standing dependency hell.

The UV CLI cheatsheet is therefore not just a list of commands; it is a comprehensive guide to adopting modern best practices in Python development. By following the structured workflow (Initialize $\rightarrow$ Add/Group $\rightarrow$ Lock $\rightarrow$ Sync $\rightarrow$ Run), developers can achieve unparalleled speed, reliability, and reproducibility across all stages of the software lifecycle.
