Executive Summary

OpenCode operates on a profoundly modular and hierarchical configuration architecture, allowing users to define system behavior at multiple levels—from global defaults down to specific function execution hooks. The entire ecosystem is governed primarily by the central opencode.json file (or its commented variant, opencode.jsonc) OpenCode Config.

This report summarizes and analyzes the vast array of configuration parameters, demonstrating that OpenCode does not rely on a single list of settings but rather an interconnected system of control levers governing five primary domains: Core System Settings, Model Behavior Tuning, External Tool Definition, Agentic Roles & Workflow Logic, Security Permissions, and Runtime Hooks (Plugins).

The parameters range from simple credential inputs (e.g., API keys under providers) to complex programmatic definitions, such as JSON schemas for tool input validation or event-intercepting hooks like tool.execute.before. Mastery of these parameters is essential for building reliable, secure, and highly specialized AI workflows, enabling developers to precisely control the LLM's decision-making process, resource consumption, and external interactions.

I. Core System Configuration: The Central Operating System (opencode.json)

The opencode.json file serves as the foundational manifest for the entire OpenCode environment. It is not merely a list of settings; it is the system's initial state machine, defining which components are active and how they interact by default OpenCode Config.

The model Parameter: Defining the Core Intelligence

The most fundamental parameter is the model key. This dictates the primary Large Language Model (LLM) that will drive the agent's reasoning and output generation. Crucially, it requires a structured identifier format: provider_id/model_id.

Analysis: The necessity of this specific format (provider_id/model_id) is critical because it allows OpenCode to abstract away the underlying API calls. Instead of needing separate keys for OpenAI's key and Anthropic's endpoint, the system only needs to know which provider and which model variant are being used, enabling seamless switching between providers without rewriting core logic Models.

Example: Setting a default model might look like: "model": "lmstudio/google/gemma-3n-e4b".

The providers Block: Credentials and Connectivity

The providers section is the secure vault for external API credentials. This block manages connectivity to services such as Anthropic, Azure OpenAI, or Amazon Bedrock Providers.

Analysis: By centralizing provider keys here, OpenCode adheres to best practices in security and maintainability. Instead of embedding sensitive keys into the workflow logic, they are managed at a single point of configuration. This structure also allows for defining fallback providers or multiple credentials for redundancy.

The plugins Block: Intercepting Time and Space

The plugins section is arguably the most advanced form of parameterization. It moves beyond simple settings and defines hooks—programmatic points in the execution lifecycle where custom code can be injected Plugins.

Analysis: Hooks are not static parameters; they are runtime configuration rules. They allow developers to intercept system events (e.g., "before a tool runs," or "after an environment variable is set") and execute custom logic, effectively allowing the user to programmatically modify the flow of execution itself. This elevates OpenCode from a simple prompt-based agent to a fully customizable development platform.

II. Model Behavior Tuning: Controlling the LLM's Mindset (LLMs)

While the model parameter defines which brain is used, the parameters within the model configuration sections define how that brain thinks. This tuning capability allows developers to optimize for specific outcomes—be it creativity, conciseness, or deep logical reasoning.

Global Model Options (options)

The options block provides global levers to adjust the LLM's operational characteristics across all connected providers. These parameters are crucial because they allow a single model definition to be optimized for multiple use cases without requiring code changes.

Detailed Parameters and Impact: 1. reasoningEffort: This parameter controls the depth of internal thought processes the LLM is encouraged to perform. A higher value forces the model to generate more detailed, step-by-step reasoning (Chain-of-Thought), which is vital for complex problem-solving but increases token usage and latency. 2. textVerbosity: This controls the expected length and detail of the final output. Setting this low can force the agent to be concise and actionable, ideal for API responses; setting it high encourages detailed explanation, suitable for reports or documentation.

Provider-Specific Overrides: The budgetTokens Example

OpenCode recognizes that different LLM providers have unique constraints and optimal usage patterns. For instance, Anthropic models may require a specific parameter like budgetTokens. By allowing these provider-specific overrides within the global configuration structure, OpenCode maintains its universal interface while respecting the technical limitations of the underlying API Models.

The Power of variants: Managing Complexity

The variants structure is a sophisticated organizational tool. Instead of creating three separate model definitions (one for 'Drafting,' one for 'Coding,' and one for 'Summarizing'), the user defines one core model and then creates named variants within it. Each variant inherits the base model but overrides specific parameters—for example, setting reasoningEffort: high only when the 'Debugging' variant is active. This prevents configuration sprawl and ensures consistency while maintaining specialized behavior Models.

III. Defining Action Space: Tools and Custom Commands

OpenCode agents are powerful because they do not just talk; they act. The parameters defining these actions—Tools and Commands—are the agent's operational vocabulary, dictating what tasks it can perform outside of pure text generation. While both allow for external functionality, their configuration methods differ significantly.

Tools: Structured API Interaction

A Tool is configured as a formal interface to an external function or service. The parameters required are highly structured and mandatory: 1. Name & Description: These define the tool's purpose, which the LLM uses in its reasoning step (the "why" it should use the tool). 2. JSON Schema: This is the most critical parameter. It dictates the exact structure of the inputs the tool requires (e.g., {"type": "string", "description": "The file path to analyze."}). The schema forces the LLM to generate valid, machine-readable arguments, eliminating ambiguity and making the interaction reliable Tools.

Analysis: By mandating a JSON Schema, OpenCode elevates tool usage from mere suggestion to guaranteed execution parameters. This is foundational for enterprise use cases where predictable data input is non-negotiable.

Custom Commands: Workflow Orchestration

Custom commands are designed less for single API calls and more for wrapping complex, multi-step workflows. They require defining a unique command name and, crucially, providing the prompt or logic that guides the LLM through the sequence of steps Commands.

IV. Agentic Roles, Plugins, and Hooks: The Deep Customization Layer

This section covers the most advanced parameters, moving beyond simple settings into programmatic control over system flow.

Agents: Defining Identity and Scope

Agents are configured by defining a dedicated role, often using structured markdown files placed in designated directories (~/.config/opencode/agents/). These definition files contain the agent's persona, its core mission statement, and its operational constraints Agents.

Analysis: The Agent configuration parameters are fundamentally about contextual grounding. They ensure that every interaction is filtered through a specific lens—a "System Prompt" writ large. An agent configured for 'Financial Analysis' will automatically constrain the LLM's output and reasoning to financial terminology, regardless of the global default settings.

Plugins: The Event Interception Mechanism

As noted previously, plugins utilize hooks, which are parameters that define when code runs. This is a profound level of control.

Example Hooks: * tool.execute.before: Allows pre-validation or logging before an external tool is called. * shell.env: Allows the programmatic setting or modification of environment variables specifically for shell operations, ensuring that sensitive data or necessary paths are available only when required Plugins.

Synthesis: The combination of Agents (defining who is acting) and Plugins (defining when code runs) provides the highest degree of control. A developer can create an agent that, upon starting a task, automatically executes a plugin hook to set specific environment variables, thereby restricting its available resources before it even attempts to call a tool.

V. Security and Resource Management: Permissions Control

The permissions section is not merely advisory; it is the security gatekeeper of the entire system. It defines the boundaries of trust between the LLM's generated intent and the actual actions taken by the agent.

Granular Action Approval

Permissions parameters allow users to define which classes of actions require explicit human approval before execution. This mechanism mitigates the risk of "hallucinated actions," where an LLM might confidently plan a destructive or costly action (like deleting files or making financial transactions) that should never run without confirmation Permissions.

Key Parameters Controlled: 1. File System Access: Rules governing read/write access to specific paths (/etc, ~/data). This prevents the agent from accidentally or maliciously traversing restricted areas. 2. External API Calls: Defining which external services (e.g., payment gateways, internal databases) are permissible targets for tool execution.

Hierarchy of Control

The configuration supports a hierarchy: Global rules can be set, but these can be overridden by specific Agent definitions or even individual Tool configurations. This ensures that while the system maintains strong default security, specialized agents can operate within necessary, tightly controlled exceptions.
